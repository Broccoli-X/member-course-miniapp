# 教培会员课时小程序产品与技术设计

- 文档状态：用户已确认，实施计划已完成，待选择执行方式
- 日期：2026-07-23
- 仓库地址：`https://github.com/Broccoli-X/member-course-miniapp.git`
- 产品范围：单机构、单校区、2C 教培/兴趣班会员管理
- 目标技术栈：微信原生小程序、Vue 3、NestJS、Prisma、MySQL

## 1. 背景与目标

机构需要一套前后端分离的会员系统，服务家长、成人学员和内部管理员。系统以线下销售、线上查询和教务执行为核心，不承接在线支付。

首期成功标准是跑通并稳定支撑以下闭环：

1. 用户通过微信注册并绑定手机号。
2. 一个账号管理本人或多个孩子的学员档案。
3. 管理员登记线下订单并向指定学员发放课程课包。
4. 学员预约班课或一对一时段。
5. 管理员签到或登记缺席，系统按课程规则自动处理课时。
6. 用户查询订单、课包、剩余课时、课时流水和上课记录。
7. 管理员发布活动，用户报名并签到，活动可选扣减指定课程课时。
8. 系统通过微信订阅消息发送预约、调课和活动提醒。

## 2. 已确认范围

### 2.1 业务边界

| 维度 | 决策 |

| 客户类型 | 首期仅 2C，不做企业客户、企业采购和员工分配 |
| 机构结构 | 单机构、单校区，不做多租户或跨校区课包 |
| 学员类型 | 同时支持成人本人和家长管理孩子 |
| 课程类型 | 同时支持班课和一对一 |

| 课时归属 | 按“学员 + 课程”独立核算，不跨课程使用 |
| 教务操作 | 首期由管理员排课、签到和纠错；老师仅作为排课资源 |

| 目标规模 | 会员不超过 1,000，日预约不超过 100 |

- 微服务、Redis、消息队列和复杂规则引擎。

## 3. 架构决策

### 3.1 方案比较

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 模块化单体 | 单一部署、事务简单、首期交付快、后续可按模块拆分 | 必须约束模块依赖，单实例故障影响全部功能 | 采用 |
| 小程序 API 与后台 API 分开部署 | 安全和发布边界更独立 | 重复配置与部署，共享事务更复杂 | 首期不采用 |
| 微服务与事件驱动 | 隔离和扩展能力强 | 运维、数据一致性和测试成本显著增加 | 与当前规模不匹配 |

## 5. 核心业务规则

### 5.1 账号与学员

1. 微信身份只负责登录；会员账号保存已验证手机号和账号状态。
2. 一个会员账号可以关联本人和多个孩子；一个学员也允许关联多个监护人账号。
3. 小程序每次操作学员资产时，后端必须校验 `AccountStudentRelation`，不能只信任前端传入的学员 ID。
4. 管理员可以先按手机号建立会员和学员；用户绑定同一手机号后关联已有会员账号。
5. 微信首次登录产生的临时账号不能创建学员或业务资产。绑定手机号时锁定手机号唯一记录：无既有账号则完成绑定；存在唯一的预建账号则在同一事务中把微信身份迁移到预建账号并停用临时账号；存在冲突则终止绑定并交由管理员处理。
6. 用户只能自动获得自己新建学员的本人/监护关系。第二监护人关系及其解除必须由管理员完成线下身份核验后操作，会员不能自行邀请或解除。
7. 手机号、姓名等相似信息不触发学员档案自动合并，防止错误暴露孩子信息。
8. 用户提交注销申请后立即禁止新增预约和报名，但保留订单、课包和历史记录的只读访问。管理员须先取消或结算未来预约和活动报名，再完成注销；注销不自动冲销订单或退课。处理完成时解除微信身份和手机号绑定，直接身份信息做匿名化。订单、课时流水和审计记录以去标识形式保留，首期不提供自动物理清理。

### 5.2 课程、规则与课包商品

课程分为：

- 班课：管理员发布具体课次，用户逐课次预约；首期不支持整期自动占位。
- 一对一：管理员发布可预约时段，容量固定为 1；老师不自行维护时间。

课程规则只覆盖首期明确需要的配置，不建设通用规则引擎：

- 单次所需课时。
- 扣课节点：预约成功或签到。
- 预约开放和截止时间。
- 取消截止时间。
- 超时取消是否扣课。
- 缺席是否扣课。

课次发布时复制课程规则形成快照。课程规则后续修改不影响已经发布的课次和既有预约。

首期始终允许用户在开课前取消。超过取消截止时间的请求记为超时取消，再按照“超时取消是否扣课”结算；开课后不允许用户取消，由管理员登记签到或缺席。

课包商品必须绑定一门课程，包含名称、售价、课时数和有效天数。售价只用于线下订单记录，所有金额均为人民币并使用 `DECIMAL(10,2)`。

创建订单明细时冻结商品名称、成交单价、课时数和有效天数，后续商品修改不得影响既有订单。订单确认日在 `Asia/Shanghai` 下作为销售课包的生效日，到期日为“生效日 + 有效天数 - 1 天”，首尾日期均包含；人工课包由管理员明确填写生效日和到期日。

### 5.3 线下订单

订单状态：

~~~mermaid
stateDiagram-v2
    state "草稿" as DRAFT
    state "已确认" as CONFIRMED
    state "已作废" as VOIDED
    state "已冲销" as REVERSED
    [*] --> DRAFT
    DRAFT --> CONFIRMED: 确认线下收款
    DRAFT --> VOIDED: 作废
    CONFIRMED --> REVERSED: 仅有 GRANT 流水且全部课时仍可用
~~~

确认订单必须在一个 MySQL 事务内完成：

1. 锁定订单并确认仍为草稿。
2. 校验每个明细的学员、课程和已冻结的销售快照。
3. 为每个订单明细创建具体课包。
4. 写入 `GRANT` 课时流水并更新“学员 + 课程”余额。
5. 将订单更新为已确认。
6. 写操作审计和通知发件箱。

`source_order_item_id` 建立唯一约束，确保重试不会重复发课。已确认订单不可直接编辑或删除。

整单冲销要求每个销售课包同时满足：除初始 `GRANT` 外从未产生其他课时流水；原始课时全部仍为可用；预占、消耗和失效均为 0；不存在预约、活动或人工调整分配。冲销写反向流水，不删除原订单。任一条件不满足时禁止冲销，只能通过有原因的人工补偿流水纠错，不提供系统退款。

### 5.4 课时账户与流水

课时严格按“学员 + 课程”隔离，区分：

- 可用课时。
- 预占课时。
- 已消耗课时。
- 已失效课时。

系统同时维护四类数据：

| 数据 | 用途 |
| --- | --- |
| 具体课包 `CoursePackage` | 保存每次订单或人工发放形成的课时分桶和到期日 |
| 汇总余额 `StudentCourseBalance` | 快速查询并作为并发加锁入口 |
| 追加流水 `HourTransaction` | 记录发放、预占、扣减、返还、失效、冲销和人工调整 |
| 分配记录 `HourAllocation` | 记录预约或活动从哪些原始课包分配课时，便于原路返还 |

规则：

1. 多个可用课包按“到期日最早、创建时间最早”分配。
2. 取消、活动取消或考勤纠错必须退回原来分配的课包。
3. 课时使用 MySQL `DECIMAL`，禁止浮点数。
4. 余额不得直接修改；所有变化必须由流水驱动，并可由流水复核。
5. 人工添加课时创建 `source_type=MANUAL` 的独立课包，要求填写课程、课时、生效日、到期日和原因。
6. 人工扣减按正常的课包分配顺序消耗现有可用课时，必须填写原因，不得使可用或预占课时为负数；人工纠错使用补偿流水，不覆盖原流水。
7. 课包到期后不可预约；上课日期必须落在课包有效期内。
8. 课包到期只处理可用课时，不失效已绑定合法未来课次的预占课时。
9. 系统每天 `00:05 Asia/Shanghai` 处理到期日早于当天的课包。若取消、活动取消或考勤纠错发生时原课包已经到期，反向课时仍退回原课包但直接计入失效课时，不恢复为可用；需要延长权益时由管理员另建人工补偿课包。

### 5.5 排课、预约与考勤

课次状态：`DRAFT → PUBLISHED → COMPLETED`，已发布课次也可以转为 `CANCELLED`。

预约前必须校验：

- 课次已发布且处于预约窗口。
- 学员对该课程有覆盖上课日期的有效课时。
- 同一学员没有重复预约。
- 学员没有重叠的课程或活动。
- 班课仍有名额；一对一容量固定为 1。
- 老师和教室没有时间冲突。

一次预约记录从 `CONFIRMED` 只能迁移到一个关闭状态：`CANCELLED_ON_TIME`、`CANCELLED_LATE`、`CHECKED_IN`、`NO_SHOW` 或 `SESSION_CANCELLED`。重复调用相同幂等请求返回原结果；使用不同请求号重复执行则返回当前状态，不重复处理课时。

按时或超时取消后，只要课次仍开放预约，学员可以重新预约；系统新建带递增尝试号的预约记录，旧记录保持不可变。同一学员和课次在任意时刻最多一个有效预约。已签到、缺席或机构取消课次后不能重新预约该课次。

预约状态与课时处理：

| 事件 | 预约时扣课 | 签到时扣课 |
| --- | --- | --- |
| 预约成功 | 立即扣减 | 先预占课时 |
| 按时取消 | 返还原课包 | 释放预占 |
| 超时取消且规则扣课 | 保持已扣 | 预占转消耗 |
| 超时取消且规则不扣课 | 返还原课包 | 释放预占 |
| 签到 | 不重复扣减 | 预占转消耗 |
| 缺席且规则扣课 | 保持已扣 | 预占转消耗 |
| 缺席且规则不扣课 | 返还原课包 | 释放预占 |
| 机构取消课次 | 无条件返还 | 无条件释放 |

即使课程配置为签到扣课，预约时也要预占课时，避免签到时余额不足。

管理员可以在课次结束后手动结算；结束 30 分钟后，定时任务自动把仍为 `CONFIRMED` 的预约转为 `NO_SHOW`，执行缺席规则，并在全部预约完成结算后把课次置为 `COMPLETED`。手动和自动结算使用同一幂等命令。

撤销签到或纠正考勤不能删除原记录。每次纠错新增一条 `AttendanceRecord` 并指向被替代记录，旧记录标记为已替代；`Booking` 保存当前有效考勤结果。纠错只反向处理原状态迁移实际产生的课时流水：预约时已扣课的课程在签到时未产生新流水，单纯撤销签到不得返还课时；签到时扣课的课程则把本次消耗按新考勤状态恢复为预占、返还或继续消耗。

调课需要重新检查老师、教室、学员时间冲突和课包有效期。新日期超出已分配课包有效期时拒绝调整，管理员应先处理受影响预约。

### 5.6 活动

活动状态：`DRAFT → PUBLISHED → ENDED`，已发布活动也可以转为 `CANCELLED`。一次报名记录从 `REGISTERED` 只能迁移到 `CANCELLED`、`CHECKED_IN`、`NO_SHOW` 或 `ACTIVITY_CANCELLED`。取消后如报名窗口仍开放，用户重新报名时新建记录；同一学员和活动在任意时刻最多一个有效报名。

活动支持：

- 报名起止时间和人数上限。
- 用户报名、取消、管理员代报名和取消。
- 活动签到和未签到状态。
- 线下费用状态：无需收费、未收、已收、免除、已线下退回。状态仅为人工信息记录，不触发在线支付或退款。
- 可选扣课。

用户只能在活动开始前取消；活动开始后由管理员或自动结算任务登记签到和未签到。首期不配置活动超时取消扣课规则。

扣课活动必须绑定一门具体课程和课时数。报名成功时预占该课程课时，签到时转为实际消耗。用户取消、未签到或机构取消时释放预占。首期活动缺席不扣课，不复制课程超时取消规则。

管理员可以在活动结束后手动结算；结束 30 分钟后，定时任务自动把仍为 `REGISTERED` 的报名转为 `NO_SHOW`、释放预占，并把活动置为 `ENDED`。手动和自动结算使用同一幂等命令。

### 5.7 微信订阅消息

通知场景：

- 预约成功或取消。
- 开课前提醒。
- 机构调课或取消课次。
- 活动报名成功、活动提醒或活动取消。
- 课包低余额或临近到期提醒。

业务事务只写 `NotificationOutbox`。后台任务轮询待发送记录，调用微信接口并记录成功、失败和重试次数。

微信发送失败不回滚订单、预约、考勤或活动状态。以“领域事件 ID + 对象版本 + 消息类型 + 接收账号”建立唯一键，避免同一事件重复发送，同时允许同一课次多次合法调课通知。取消预约、取消活动或调课时，系统作废尚未发送的旧提醒，并按最新对象版本重建提醒；已经发送的消息只追加更正通知。只有用户已授权对应订阅模板时才发送。

若 worker 在请求微信后、保存发送结果前中断，系统无法可靠判断微信是否已接收。此类记录标记为“投递结果未知”，不得自动重发；管理员核对后再决定关闭或人工重试，避免把外部调用误当成数据库内的恰好一次事务。

### 6.1 关键约束

- 同一学员和课次最多存在一个有效预约。
- 同一学员和活动最多存在一个有效报名。
- 每个订单明细最多创建一个销售课包。
- 订单明细保存商品和成交数据快照；确认后的订单和快照不可变。
- `ClassGroup` 是班课批量排课模板，只组织课程、老师和课次，不保存固定学员名单，也不自动创建整期预约；一对一课次不创建班级且容量固定为 1。
- `ClassSession` 保存来源规则版本 ID 及完整规则快照；后续只使用快照结算。
- 课程规则快照随课次发布后不可变。
- 被订单、课次、预约或流水引用的会员、学员、课程、老师和教室只能停用或归档。
- 所有可变关键表包含创建时间、更新时间和版本号；仅追加的流水、分配和审计表包含创建时间且禁止更新/删除。状态迁移使用条件更新或版本号防止覆盖。
- 时间统一存储为 UTC，业务规则和展示使用 `Asia/Shanghai`。取消截止时刻等于边界视为按时，超过才算超时。
- `AuditLog.actor_type` 为 `ADMIN`、`MEMBER` 或 `SYSTEM`；对应操作人 ID 可为空，仅系统定时任务使用 `SYSTEM`。

## 7. API、鉴权与错误处理

### 7.1 API 边界

- 小程序接口：`/api/mini/v1`。
- 管理后台接口：`/api/admin/v1`。
- 两套 Controller 和 Guard 相互隔离，复用应用服务和领域模块。
- 查询接口采用资源化 REST；确认订单、签到、撤销签到等使用表达业务意图的命令接口。
- 确认订单、预约、取消、签到、报名和人工调整要求 `Idempotency-Key`；同一个 Key 重试返回首次结果，不再次执行领域命令。
- 所有列表接口统一分页、筛选和排序格式。

### 7.2 鉴权

小程序：

1. 前端获取微信登录 code。
2. 后端调用微信接口换取 openid/unionid，创建或查找微信身份。
3. 后端签发短期 Access Token 和可轮换 Refresh Token。
4. 用户通过微信手机号能力绑定已验证手机号。
5. 每次学员操作同时校验会员身份和账号-学员关系。

后台：

- 管理员使用账号密码登录。
- 密码使用 Argon2id 强哈希保存。
- 登录失败限流，连续失败触发短时锁定。
- 支持会话过期、刷新和主动停用管理员账号。
- 首期管理员权限相同，但所有关键写操作记录操作人。

### 7.3 统一错误契约

~~~json
{
  "code": "SESSION_FULL",
  "message": "该课次名额已满",
  "traceId": "req_...",
  "details": null
}
~~~

| HTTP 状态 | 场景 |
| --- | --- |
| 400 | 参数格式错误 |
| 401 | 未登录或登录已过期 |
| 403 | 无权访问该学员或管理资源 |
| 404 | 资源不存在或已归档不可见 |
| 409 | 重复操作、名额竞争或状态已经变化 |
| 422 | 课时不足、时间冲突、课包过期或业务规则不满足 |
| 429 | 登录或接口请求过于频繁 |
| 500 | 未预期错误；隐藏内部细节并返回 traceId |

前端必须识别并提供可执行提示的业务错误包括：

- `PHONE_BINDING_REQUIRED`
- `STUDENT_FORBIDDEN`
- `SESSION_NOT_BOOKABLE`
- `SESSION_FULL`
- `DUPLICATE_BOOKING`
- `TIME_CONFLICT`
- `HOURS_INSUFFICIENT`
- `PACKAGE_NOT_VALID_FOR_SESSION`
- `STATE_CHANGED`

### 7.4 并发与一致性

- 最后一个名额：容量检查、计数更新和预约/报名创建在同一事务，并锁定课次或活动。
- 课时竞争：预约、报名、人工调整和到期处理锁定 `StudentCourseBalance` 及相关课包。
- 学员时间冲突：预约课程或报名活动时先锁定 `StudentProfile`，再重新查询该学员的重叠有效预约和报名。
- 老师/教室冲突：发布或调课时按固定 ID 顺序锁定涉及的 `Teacher`、`Classroom` 记录，再重新查询重叠课次。
- 同时取消与签到：使用状态条件更新或版本号，只允许一个迁移成功。
- 重复请求：命令接口使用幂等请求号，课时流水使用唯一业务幂等键。
- MySQL 死锁：统一锁顺序，并对可重试事务做有限次数重试。

## 8. 安全、隐私与审计

- 全链路 HTTPS。
- 微信密钥、数据库密码和 Token 密钥只从部署环境的密钥管理读取，不写入仓库。
- 手机号在后台和日志中脱敏，应用日志不记录 Token、微信密钥和完整手机号。
- 活动富文本使用白名单清洗，防止存储型 XSS。
- 文件上传由后端签发受限凭证，校验文件类型、大小和访问范围。
- ORM 使用参数化查询；所有 DTO 做类型、长度和枚举校验。
- 登录、验证码/手机号绑定和高频查询实施速率限制。
- 操作审计保存业务对象、动作、修改前后值、操作人、原因、时间和请求号。
- 提供用户协议、隐私政策、手机号授权说明和账号注销申请入口。

## 9. 部署与运行

### 9.1 首期拓扑

- Nginx/TLS 入口。
- Vue 3 管理后台静态资源。
- 单实例 NestJS 应用。
- MySQL。
- 云对象存储。
- 微信开放接口。

首期不引入 Redis 和消息队列。可靠通知使用 MySQL 发件箱表和 NestJS 定时轮询任务。定时任务使用数据库锁避免未来多实例部署时重复执行。

### 9.2 非功能目标

| 项目 | 目标 |
| --- | --- |
| 容量 | 1,000 会员、日预约 100 |
| 性能 | 50 个并发用户、读写请求 80/20 的基准负载下，常规业务 API P95 不超过 500ms，不含微信和对象存储外部延迟 |
| 并发 | 对最后名额、最后课时和重复提交做专项并发测试 |
| 备份 | MySQL 每日备份，生产数据库变更前额外备份 |
| 恢复 | RPO 不超过 24 小时、RTO 不超过 4 小时，并定期做恢复演练 |
| 可观测性 | 请求 traceId、结构化日志、业务审计、任务执行记录 |
| 告警 | 5xx、登录异常、通知积压/失败、定时任务失败、数据库容量和备份失败 |

开发、测试和生产环境相互隔离，使用独立数据库、密钥和微信配置。

## 10. 测试策略

### 10.1 测试分层

| 层级 | 覆盖内容 |
| --- | --- |
| 领域单元测试 | 状态机、课程规则快照、课包分配、有效期、取消边界、反向流水 |
| MySQL 集成测试 | 事务、唯一约束、行锁、死锁重试、幂等、通知发件箱 |
| API 契约测试 | 鉴权、学员归属、DTO 校验、业务错误码、分页和幂等头 |
| 端到端测试 | 小程序和管理后台的完整业务旅程 |
| 运行验证 | 微信真实账号联调、备份恢复、数据库迁移和告警验证 |

CI 必须执行格式检查、类型检查、单元/集成测试、前后端构建和数据库迁移校验。

### 10.2 必须通过的验收场景

1. 管理员预建会员和孩子后，用户绑定同一手机号并看到正确档案；冲突账号不自动合并。
2. 重复确认同一线下订单只生成一套课包和一次 `GRANT` 流水。
3. 多个课包按最早到期优先预占，取消后准确退回原课包；原课包已过期时返还量直接进入失效课时。
4. 多人抢最后一个名额时只有一人成功，其他请求返回 `SESSION_FULL`。
5. 取消截止边界、超时取消、缺席和机构取消均按课次规则快照结算。
6. 签到与取消同时发生时只有一个状态迁移成功。
7. 撤销签到只反向处理原签到实际产生的课时流水，并记录新的考勤记录和操作原因。
8. 扣课活动必须绑定课程；报名取消、未签到或活动取消释放预占。
9. 微信消息失败不影响业务结果，任务进入重试且不重复发送。
10. 每次订单、课时、考勤和活动关键修改都能定位操作人、原因与请求号。
11. 同一学员并发预约两个重叠课次时只允许一个成功；并发发布同一老师或教室的重叠课次时只允许一个成功。
12. 取消后重新预约或报名会创建新尝试，旧记录和原课时流水保持不变。
13. 调课或取消后旧提醒被作废，新版本提醒可以正常生成和发送。

## 11. 分阶段交付

### M1：会员与课时资产

- 微信登录和手机号绑定。
- 本人/孩子学员档案。
- 课程和课包商品。
- 后台线下订单确认与冲销。
- 具体课包、汇总余额、人工调整和课时流水。
- 小程序订单、课包和课时查询。

验收闭环：建档 → 录单 → 发课 → 小程序查询订单与余额。

### M2：教务与上课闭环

- 老师、教室和班级。
- 班课批量排课和一对一可约时段。
- 预约、取消、容量与冲突检测。
- 签到、缺席、撤销签到和考勤纠错。
- 课时预占、扣减和返还。

验收闭环：排课 → 预约 → 签到 → 扣课 → 可追溯纠错。

### M3：活动与生产就绪

- 活动发布、报名、取消和签到。
- 线下费用状态和可选课程扣课。
- 微信订阅消息和失败重试。
- 工作台、数据导出和操作审计。
- 用户协议、隐私、注销、监控、备份和发布检查。

验收闭环：发布 → 报名 → 签到/扣课 → 通知与审计。

## 12. 最终验收定义

产品达到首期可交付状态必须同时满足：

1. M1、M2、M3 的业务闭环全部通过。
2. 关键课时余额可以由课包和追加流水复核，不存在无来源余额。
3. 重复请求、并发名额和同时状态迁移测试通过。
4. 小程序只能操作当前账号有关系的学员。
5. 管理员关键操作全部可审计。
6. 微信消息失败不会破坏业务一致性。
7. 核心回归、微信联调、隐私入口、数据库备份恢复和生产监控验证完成。
